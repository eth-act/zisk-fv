Glossary

The shared vocabulary. Every lesson uses these terms with these meanings — adhere to them when reasoning or writing about the repo.
Build & generation Circuit / AIR (RHS) Spec (LHS) Proof tower Trust gate Completeness

Build & generation how inputs are produced

Nix flake / flake.lock
The reproducible build definition. flake.lock pins every upstream input (Sail, sail-riscv, ZisK, pil2-* sources, nixpkgs) by content hash — it is the audit surface for what the build consumes. flake.nix, nix/, flake.lock
nix run .#populate
One command that builds the three generated derivations and copies their outputs into the tree. Run once before lake build. nix/populate.nix
PIL / PIL2
The constraint DSL ZisK's circuit is written in. The pil2-compiler (Node) composes every AIR's algebraic constraints into one artifact.
.pilout
The protobuf output of the PIL2 compiler — all composed algebraic constraints. build/zisk.pilout
pil-extract
The Rust tool that reads .pilout and emits per-AIR Lean constraint files, the operation-bus Buses.lean, the memory-bus MemoryBuses.lean, and ArithTable.lean. tools/pil-extract → build/extraction/Extraction/*.lean (gitignored)
cachix
Binary cache for the Nix derivations. A cache hit turns the ~30-min cold build into seconds; CI probes it to pick a runner size. zisk-fv.cachix.org
Aeneas
A Rust→Lean extraction tool. Used on the zisk/ submodule to extract the production lowering path (RISC-V → ZisK rows) into Lean, backing the completeness harness. zisk/ submodule, build/aeneas-production-extraction/

Circuit / AIR — the RHS what ZisK computes

AIR (Algebraic Intermediate Representation)
One circuit's constraint set. ZisK is composed of ~22 AIRs (Main, Binary, BinaryExtension, Arith, Mem, MemAlign, …).
Valid_<AIR>
A Lean record of named columns + simp lemmas wrapping a generated AIR, whose declared constraints mirror the PIL constraints. Over-strong constraints here make theorems vacuous — see constructibility in the trust glossary. ZiskFv/Airs/Valid_<AIR>
Operation bus / op-bus
The model (in Airs/OperationBus) that mediates how an instruction's execution maps to circuit rows. Its matches_entry predicate replaces explicit interaction tracking. ZiskFv/Airs/
Memory bus
The analogous model for memory reads/writes (MemoryBuses.lean, Airs/Mem, MemAlign*).
Goldilocks / FGL
The prime field the circuit lives in (p = 2⁶⁴ − 2³² + 1). FGL is the Lean Field instance. ZiskFv/Field/Goldilocks.lean
Clean
A Lean ZK-circuit DSL (Verified-zkEVM/clean). The AirsClean/ tree formalizes the AIR ensemble in Clean; it replaced the retired OpenVM-style Circuit layer. ZiskFv/AirsClean/ (73 files), build/clean-lean

Spec — the LHS the reference truth

Sail
The language the official RISC-V spec is written in. sail-riscv is compiled (via the Sail compiler) into Lean — that compiled spec is the LHS reference every opcode is proved against. build/sail-lean/ (the LeanRV dependency)
execute_instruction
The Sail entry point: given a decoded instruction and a state, produce the next state. The LHS of every equivalence theorem.
Pure spec
Per-opcode bridge files restating the Sail semantics in a proof-friendly form. ZiskFv/SailSpec/

Proof tower where LHS meets RHS

EquivCore/<Op>
The real per-opcode proof: Sail.execute = bus_effect.2. Plus shared Bridge/, Promises/, WriteValueProofs/. ZiskFv/EquivCore/ (93 files)
Promise hypothesis
A caller-supplied assumption a theorem takes as a parameter instead of proving. The project's trust residue lives here.
Promise discharge / wrapper
Replacing promise hypotheses with derivations from the trust ledger. Done per opcode in Compliance/Wrappers/<Op> (formerly FromTrust/), producing Compliance.equiv_<OP>. ZiskFv/Compliance/Wrappers/
equiv_<OP> (canonical)
The canonical per-opcode theorem in channel-balance form. 63 of them, one per RV64IM opcode. Kept OUTPUT-EQ-free by the trust gate. ZiskFv/Equivalence/<Op> (63 files)
Channel balance
The canonical statement form: Sail.execute = state_effect_via_channels. ZiskFv/Channels/
Dispatch / OpEnvelope
Per-family dispatchers aggregate the wrappers; the global theorem routes all 63 opcode surfaces through a 63-arm OpEnvelope sum type. ZiskFv/Compliance/Dispatch/
Global theorem
ZiskFv.Compliance.zisk_riscv_compliant_program_bus — the top-level verification claim. Conditioned, not unconditional: takes an OpEnvelope plus three hypotheses — h_bridge : aeneasBridgeTrust, h_memory_construction, and h_known_bugs : Defects.NoKnownDefect — and concludes the channel-balance equivalence for that arm. ZiskFv/Compliance.lean:95
aeneasBridgeTrust
An OpEnvelope field / global-theorem hypothesis standing in for the Aeneas-extracted lowering bridge until generated Aeneas Lean is imported by main Lake. Part of the residual trust — the "0 axioms" claim holds because trust lives in hypotheses like this (tracked in the caller-burden ledger), not in axioms.
Defects.NoKnownDefect / trust/defects.md
The known-defect carve-out. The global theorem holds only for envelope arms outside the ledgered defect regions — ZisK v0.17.0 has open claim-weakening defects this repo found. "Green" means "compliant modulo known defects," not "bug-free." trust/defects.md

Trust gate the meta-layer that guards the claim

Trust gate
Two layers of mechanical checks: V1 syntactic (check-all.sh, no build) and V2 semantic (check-all-semantic.sh, consumes oleans). Both must pass. trust/scripts/
Trust ledger
The recorded set of trusted axioms + their source-text hashes; currently 0 axioms. trust/trusted-base.md, trust/generated/baseline-axioms.txt
Caller-burden ledger
One line per parameter binder on every canonical theorem (name + category + type). The diff is the audit surface: a real discharge removes more lines than it adds. trust/generated/baseline-caller-burden.txt
Anti-laundering metric
The rule that both the hypothesis-count and caller-burden baselines must shrink (or hold) — catching refactors that merely rename / split / re-home trust instead of discharging it.
Constructibility
The requirement that a Valid_<AIR> instance is actually producible by a real ZisK trace. Over-strong validators make equivalence theorems vacuously true.

Completeness the coverage side

rv64im_completeness
An acceptance/coverage theorem: every Sail-executable RV64IM raw word (outside the recorded FENCE decode gap) is accepted by the production ZisK path. Interface-mediated by the Aeneas extraction gate. ZiskFv/Completeness/Rv64im
Honest-row constructibility
The Clean-side completeness proofs that each of the 17 fields has a buildable honest row (scope: row-local, not cross-row trace completeness).
