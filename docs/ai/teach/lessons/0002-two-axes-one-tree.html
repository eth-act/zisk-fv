Lesson 02 · zisk-fv architecture

Two Axes, One Tree

The tree proves two different things about ZisK, and they are duals. Soundness: nothing ZisK accepts is a lie about RISC-V. Completeness: nothing true about RISC-V is left uncovered. Neither is worth much alone — and they run end-to-end side by side, layer for layer.

Validated against main @ e731db56, 2026-06-22. Supersedes Lesson 01's soundness-weighted map.

Your win — Draw the repo as two co-equal axes, each running raw-word → headline; name each layer's job on each axis; and say where each headline is discharged (in-tree vs the Aeneas seam).

1The two claims, precisely

Pin the exact statements first — everything else hangs off these.

Soundness
accepted trace ⇒ Sail spec agrees
For every row of an accepted ZisK trace, the Sail spec's execute_instruction equals the state effect ZisK's circuit commits to. Per-opcode, climbed to one trace-level theorem. root_soundnessZiskFv/Soundness.lean:21
Completeness
Sail-executable word ⇒ ZisK covers it
Every Sail-executable RV64IM raw word is decoded, lowered, materialized and soundness-input-covered by ZisK's circuit surface — except explicitly recorded decode gaps. root_completenessZiskFv/Completeness/Rv64im.lean:5919
Why you need both
Soundness alone is vacuously satisfiable: a circuit that accepts nothing never disagrees with Sail. Completeness rules that out — it forces the circuit to actually implement the ISA. Soundness = “no accepted lie.” Completeness = “no rejected truth.” Together they say ZisK faithfully and totally realizes RV64IM, modulo shared carve-outs (§4).

3The completeness vocabulary

The soundness side you mostly know from Lesson 01. The completeness side has its own small algebra, all hanging off one record:

  • Rv.Interface — abstracts ZisK's decode/lower/materialize surface as a Lean structure.Completeness/Rv.lean:23
  • LoweringComplete, RowMaterializationComplete, OpcodeCoverageComplete — the three “the circuit can build it” obligations.Rv.lean:50,60,55
  • SailExecutableContainedIn — the containment direction: Sail-runnable words ⊆ supported decode.Rv.lean:113
  • SoundnessInputComplete — the bridge predicate: coverage delivers exactly the inputs the soundness theorems demand. This is the only place the two axes touch by name.Rv.lean:143
  • knownGap — the recorded decode carve-out (e.g. FENCE).Rv.lean:35

4Shared carve-outs — the real integration point

Both axes carry the same exclusions, and that is what makes them one story rather than two:

  • Decode gaps (knownGap / …AvoidingKnownDecodeBugs) — FENCE-style words ZisK doesn't decode.
  • Known bugs — the DIV/REM signed remainder-bound defect the project itself found. Soundness narrows it via h_known_bugs; completeness via AvoidKnownBugs.trust/defects.md · Rv.lean:75

A re-architecture flag: the carve-out set is stated twice, once per axis, with no shared source of truth. Candidate for unification.

The seam to remember — The two arcs do not cross-reference in code. AcceptedTrace (soundness) and Rv.Interface (completeness) are independent Lean abstractions of “the same” ZisK execution. SoundnessInputComplete is the one named bridge. Whether they should share a substrate is a live re-architecture question — hold it for the build/CI lesson.
Doc check — README.md and CLAUDE.md still frame the project as the soundness arc and name only zisk_riscv_compliant_program_bus. They under-draw completeness too. Trust the tree, not the prose.
