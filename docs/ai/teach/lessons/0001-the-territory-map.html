2What each territory is for

Re-arch lens — Airs/ (legacy bus/Valid model) and AirsClean/ (generated Clean components) are two circuit-side stacks bridged together — the same duplication seam as before. Still a live re-arch question; a later lesson dissects it. RHS (circuit). pil-extract drops generated constraints into build/extraction/. Airs/ wraps them as named-column Valid_<AIR> records plus the operation-bus / memory-bus model. AirsClean/ is the Clean-DSL formalization. ZiskCircuit/ states the circuit's arithmetic semantics per opcode.

LHS (spec). build/sail-lean/ is the official RISC-V spec compiled to Lean; SailSpec/ is the thin per-opcode bridge.

The tower — bottom (stable). EquivCore/<Op> does the real Sail-vs-circuit proof; Compliance/Wrappers/<Op> discharges the row/table facts; Equivalence/<Op> is the public channel-balance equiv_<OP>; Compliance.lean aggregates via OpEnvelope into the old global theorem.

This is the big change. The old global theorem takes an OpEnvelope as a hypothesis — i.e. it assumes the per-row correspondence facts. The new top constructs that envelope from an accepted trace, so those facts become derivations, not assumptions. The tower — new top. Compliance/Construction*.lean (20 modules) hold per-opcode construction_<op>_sound theorems that build the inputs. Compliance/TraceLevelExport.lean exports them to one statement, root_soundness: given an accepted trace, a program binding, a per-row classification, and per-row defect-exclusion, every row satisfies the canonical channel-balance conclusion — with no caller-supplied OpEnvelope. ZiskFv/Soundness.lean:21

Don't conflate — the trace-export's AcceptedTrace lives in Compliance/AcceptedTrace.lean (the soundness side). It is not the completeness layer; the two don't reference each other. "Accepted trace" = a trace the ensemble accepts; "completeness" = every instruction is accepted. Different claims. The other axis — completeness. Everything above is the soundness direction: if ZisK accepts a row, Sail agrees. ZiskFv/Completeness/ (4 files) proves the dual — coverage: every Sail-executable RV64IM instruction, outside recorded decode gaps, is accepted by the production ZisK decode/lower/materialize path. The endpoint is root_completeness (Completeness/Rv64im.lean:5919), mediated by the Aeneas extraction gate. It's a separate claim, not a rung in the compliance tower — which is exactly why it isn't in the climb drill below.

3The shift: assume → construct

the headline is moving up the tower

Old (still present): zisk_riscv_compliant_program_bus (env : OpEnvelope) … : env.exec_eq — proves Sail = circuit given an envelope you hand it. The per-row correspondence is assumed.

New: root_soundness (trace : AcceptedTrace) (binding) (rowData) (h_known_bugs) : ∀ i, StepComplianceStrong … — the envelope for each row is constructed inside, from the trace. All 63 archetypes are covered via three routes (env-constructed ALU arms; direct-lift control/U/load/store/unsigned-M; defect-narrowed signed-M + FENCE). Trust closure: 0 project axioms.

This is the project answering, in code, the exact question this map raised last time: should the per-opcode "promises" be derived rather than assumed? At trace level, for an accepted trace, they now are. The residual moved from "build an OpEnvelope" to "supply an accepted trace + a per-row classification + the defect-exclusion." We'll unpack what those residuals are in a later lesson.

4What "green" means — and a caution

lake build typechecks ⇒ the per-opcode theorems, the old global theorem, and the new trace-level export all hold in Lean's kernel. The trust gate ⇒ the claim's shape hasn't been weakened (0 axioms; now also the strong-export closure + construction-binder baselines).

Caution — docs lag code. Both README.md and CLAUDE.md still name zisk_riscv_compliant_program_bus as "the verification claim" and say nothing about the construction layer or the trace-level export. For this map I read the tree, not the prose. Treat the in-repo narrative docs as a starting point to verify, never as ground truth — exactly the discipline a re-architecture needs.
