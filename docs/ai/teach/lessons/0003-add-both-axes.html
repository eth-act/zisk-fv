Lesson 03 · zisk-fv architecture

ADD, Both Axes

One opcode, traced up both arcs at once. Soundness asks “does this one ADD row match Sail?” Completeness asks “is every ADD word covered?” They start from the same encoding, climb two different towers, and — the punchline — never meet inside the kernel.

Validated against main @ e731db56, 2026-06-22. Builds on Lesson 02.

Your win — Recite ADD's soundness tower and completeness ladder rung by rung (with the file each lives in), say what each axis quantifies over, and name precisely where the join is — and isn't.

1One encoding, two questions

ADD is the R-type word funct7=0, funct3=0, opcode=0x33 over any register triple. Both axes start here and ask opposite questions.

ADD encoding
[ funct7=0000000 | rs2 | rs1 | funct3=000 | rd | opcode=0110011 ]
Soundness → take one circuit row whose decoded op is OP_ADD; show Sail's execute agrees with the state effect ZisK commits.
Completeness → take the whole set { rawRType 0 rs2 rs1 0 rd 0x33 } (32×32×32 words); show ZisK decodes/lowers/materializes/covers every one.

Read bottom-to-top. Each rung says what it actually does to the rung below it — not just its name. Left: the equivalence tower (one concrete row). Right: the coverage ladder (a set of 32-bit words).

So “assume an OpEnvelope → construct it from a trace” added a layer above the old headline; the old theorem is still load-bearing in every per-row proof. Worth weighing in the rebuild: two headline theorems, one stacked on the other.

3What the soundness proof actually proves

This is the intellectual content the rung names hide. The Main AIR holds the operands and result as 32-bit lanes — a_0,a_1 = lo/hi of r1, b_0,b_1 = lo/hi of r2, c_0,c_1 = lo/hi of rd. The actual 64-bit addition happens in the Binary AIR, byte by byte:

  • The Binary row exposes 8 result bytes free_in_c_0 … free_in_c_7 and 7 inter-byte carries carry_0 … carry_6. Each byte's validity comes from the static binary table's wf_properties (§ above): range_conditions (it's a genuine byte, cin a bit) plus wf_ADD (c_byte = (cin+a+b)%256, cout = (cin+a+b)/256) — surfaced here as c0_lt … c7_lt and the carry equations cin_eq/pi_ne.
  • byte_chain_discharge_64_of_static_row (EquivCore/Bridge/Binary.lean:1919, invoked at Add.lean:413) chains those into: the recomposition Σ free_in_c_k · 256ᵏ equals the true sum of the operand bytes.
  • carry_7_zero_ADD_of_static_chain (Bridge/Binary.lean:2176, invoked at Add.lean:417) pins the 8th carry to 0 — ADD has no carry-out of bit 63; the result wraps mod 2⁶⁴, exactly matching the spec's BitVec 64 add.
  • The proof then shows Main's output lanes equal the byte recomposition: c_0 = Σ_{k<4} byteₖ·256ᵏ, c_1 = Σ_{4≤k<8} byteₖ·256ᵏ (Add.lean:422–431), i.e. rd = r1_val + r2_val.

So the equation execute … = (bus_effect …).2 bottoms out in: the circuit's byte-decomposed carry-chain sum, with the top carry forced to zero, equals the spec's wrapping 64-bit add. Everything above this rung is plumbing that delivers a validated Binary row and re-dresses the conclusion.

4Where they join — and where they don't

Tower 2's top rung includes RTypeRegisterSoundnessInputComplete. The name promises the handshake: coverage should deliver exactly the inputs the soundness side consumes. Unfold it and you get ∀ raw in shape, ziskLowerable raw → ziskSoundnessInput raw (Rv.lean:146). So far so good — until you ask what ziskSoundnessInput is.

The join is nominal, not structural
ziskSoundnessInput is an abstract field of Rv.Interface — just RawInstruction → Prop (Rv.lean:29). It is never tied in-tree to the soundness world's concrete RowData_add / AcceptedTrace. Verified: Compliance/ never mentions Completeness, and Completeness/ touches Compliance only in two FENCE carve-out comments. The two ADD proofs never compose in the Lean kernel. The handshake is intended — the names line up — but it lives in the out-of-repo Aeneas harness, not in lake build.
Re-architecture flag — the biggest structural seam
This is the central thing to weigh for the rebuild. A unified architecture could make ziskSoundnessInput raw definitionally produce the RowData_add the soundness theorem demands — so a green lake build would compose both axes end-to-end for ADD, instead of leaving the join to Aeneas. Today the two arcs are independent abstractions of “the same” ZisK execution, bridged only by matching names.
